Architectural Paradigm and Hardware Topology1.1 Evolution of the Thingy Prototyping PlatformThe transition from the Nordic Thingy:91 to the Nordic Thingy:91 X represents a fundamental architectural shift in the design of cellular IoT prototyping platforms, necessitating a complete re-evaluation of firmware update mechanisms. While the preceding generation relied on the nRF9160 System-in-Package (SiP) paired with an auxiliary nRF52840 System-on-Chip (SoC), the Thingy:91 X introduces a more sophisticated topology centered around the nRF9151 SiP and the dual-core nRF5340 SoC.1 This evolution is not merely an upgrade in processing power but a redefinition of the board controller's role. In traditional Development Kits (DKs), a dedicated interface MCU—typically a SEGGER J-Link OB—manages the USB-to-UART bridging and Serial Wire Debug (SWD) transactions, abstracting these complexities from the user.2 The Thingy:91 X, designed for high-density integration and field deployment, omits this dedicated debugger silicon. Instead, it delegates the critical responsibilities of USB connectivity, board management, and inter-chip communication to the nRF5340 SoC itself.3This architectural decision has profound implications for developers seeking to integrate USB flashing capabilities into their custom projects. Unlike a standard DK where the USB port is functionally distinct from the application processor, the USB-C connector on the Thingy:91 X is physically routed directly to the nRF5340.5 The nRF9151 SiP, which houses the cellular modem and the primary application core, possesses no physical USB interface.5 Consequently, any data exchange between a host computer and the nRF9151—whether for firmware updates, AT command injection, or modem tracing—must be actively mediated by firmware running on the nRF5340. This creates a dependency chain where the accessibility of the nRF9151 is entirely contingent upon the operational state and software configuration of the nRF5340.1.2 The nRF5340 as a Software-Defined BridgeThe nRF5340 SoC acts as the gatekeeper for the entire system. It is a dual-core device featuring an Application Core (ARM Cortex-M33, 128 MHz) and a Network Core (ARM Cortex-M33, 64 MHz).2 In the context of the Thingy:91 X, the Application Core handles the high-speed USB peripheral (USBD) and orchestrates the routing of data streams to the nRF9151 via internal UART connections.6 This setup is functionally distinct from a hardware pass-through; it is a software-defined bridge where data is packetized, buffered, and re-transmitted.Implementing USB flashing for the nRF9151 therefore requires the deployment of a specific class of firmware on the nRF5340, often referred to as the "Connectivity Bridge".8 This firmware must instantiate a USB Composite Device that exposes Communication Device Class (CDC) Abstract Control Model (ACM) endpoints to the host operating system. These virtual serial ports serve as the tunnel through which the Simple Management Protocol (SMP) packets—used by the MCUboot bootloader—are transported to the nRF9151. The developer must essentially recreate the functionality of a J-Link OB using the nRF Connect SDK (NCS) libraries, integrating this bridge logic alongside any custom Bluetooth Low Energy (BLE) or sensor acquisition code intended for the nRF5340.71.3 Physical Interconnects and Signal IntegrityThe viability of this bridging mechanism relies on specific hardwired connections between the nRF5340 and the nRF9151 on the PCA20065 printed circuit board (PCB). Analysis of the hardware documentation and device tree sources reveals a dedicated set of traces allocated for this purpose. These connections are not general-purpose GPIOs in the user's application context but are reserved infrastructure for the bridge.The primary data path consists of a UART interface with hardware flow control. The nRF5340's transmit (TX) pin connects to the nRF9151's receive (RX) pin, and vice-versa. Hardware flow control (RTS/CTS) is non-negotiable in this context due to the potential throughput mismatch between the high-speed USB bulk transfers (up to 12 Mbps) and the physical UART baud rate (typically 115200 or 1 Mbps).9 Without flow control, the internal buffers on the nRF9151 could overflow during a firmware upload, leading to corrupted images and a failed update process.Furthermore, a critical control line exists between the two chips: the Reset line. The nRF5340's pin P0.24 is hardwired to the nRESET pin of the nRF9151.10 This connection is vital for the "Serial Recovery" mechanism used by MCUboot. To initiate a firmware update, the nRF9151 must be forced into its bootloader mode. Since the user cannot physically access the reset button (SW4) without disassembling the device casing, the nRF5340 firmware must assert this line (drive P0.24 low) in response to a specific trigger from the USB host.10 This software-controlled reset capability allows for automated flashing scripts and seamless developer workflows.1.4 Electrical Considerations for USB RobustnessImplementing robust USB functionality on the nRF5340 requires careful attention to the electrical characteristics of the VBUS interface. The nRF5340 integrates a dedicated internal voltage regulator (VREGUSB) that converts the 5V VBUS supply to 3.3V for the USB signaling interface (D+ and D- pull-ups).11 The stability of this regulator is paramount for maintaining a valid USB enumeration state.A significant detail emerging from the hardware revision history of the Thingy:91 X is the modification of the VBUS series resistor, R10. In the transition to the v1.0.0 release (PCA20065), the footprint for R10 was enlarged from 0201 to 0402.12 This modification addresses the thermal and transient energy dissipation requirements during VBUS insertion. When a USB cable is plugged in, mechanical bounce and the inductance of the cable can generate significant voltage spikes (ringing) and inrush currents. A resistor with a larger physical package (0402) offers superior pulse load capability compared to a 0201 component. For developers designing custom carrier boards based on the Thingy:91 X reference, adhering to this specification is critical to prevent latent hardware failures where the USB interface becomes unresponsive due to resistor burnout or regulator damage.132. Firmware Architecture: The nRF5340 Connectivity BridgeTo satisfy the user's requirement of adding USB flashing to their project, the firmware running on the nRF5340 must be architected to serve as a transparent data pipe. This involves configuring the Zephyr RTOS USB device stack, implementing the CDC ACM class, and managing the physical UART interface with low-latency constraints.2.1 The Connectivity Bridge Application StructureThe "Connectivity Bridge" is not merely a sample application but a foundational component of the Thingy:91 X ecosystem. Located in the nRF Connect SDK at applications/connectivity_bridge 8, this firmware transforms the nRF5340 into a multifunction USB device. For a custom project, the developer must determine whether to use this application as-is or to merge its logic into their own firmware.If the user intends to run custom logic on the nRF5340 (e.g., edge processing of sensor data or a custom BLE GATT server) while retaining the ability to flash the nRF9151, the bridge logic must be integrated as a background service. This requires a multi-threaded architecture where the USB-to-UART bridging runs in a high-priority thread to prevent data starvation, while the application logic runs in a lower-priority thread.The Connectivity Bridge typically exposes two distinct CDC ACM interfaces:CDC ACM 0 (Primary): This interface maps to the nRF9151's primary UART (UART0). It serves as the console for application logging and the transport layer for MCUboot Serial Recovery (DFU).CDC ACM 1 (Secondary): This interface maps to a secondary UART (UART1), often utilized for modem trace logs or GNSS NMEA data streams.8The standard configuration also includes a Mass Storage Class (MSC) instance, which presents a small virtual drive containing configuration files (e.g., README.txt). While useful for documentation, the MSC class consumes significant RAM and Flash resources. For a custom project focused on efficiency, removing the MSC instance is a recommended optimization to free up resources for the user's application logic.82.2 USB Device Stack ConfigurationEnabling the USB interface requires specific Kconfig definitions in the nRF5340's prj.conf file. The Connectivity Bridge application includes support for the Nordic UART Service (NUS), although it is disabled by default.14 Enabling this service (CONFIG_BRIDGE_BLE_ENABLE=y) allows for DFU packets to be transmitted over BLE to the nRF5340, which then forwards them to the nRF9151 via UART.While the user's request specifically mentions "USB flashing," understanding the NUS capability provides a robust fallback mechanism. If the USB port becomes physically damaged or inaccessible in a field deployment, the NUS bridge allows for firmware recovery using a mobile device or a BLE-enabled gateway. This aligns with the "high availability" design philosophy often required in professional IoT deployments.2.4 Managing the Reset TopologyThe software control of the hardware reset line (P0.24) is implemented via the GPIO driver. The bridge firmware must configure P0.24 as an output, initialized to a logical High (inactive) state. To trigger a reset, the firmware drives the pin Low for a defined duration (typically 10-100ms) before returning it to High.10The trigger for this reset event is often tied to the DTR (Data Terminal Ready) signal of the CDC ACM interface. When a terminal program connects and asserts DTR, the nRF5340 can be configured to pulse the reset line. However, for DFU operations, a more specific trigger mechanism—such as a specific baud rate setting (e.g., 1200 baud magic number) or a vendor-specific USB control transfer—is preferred to avoid accidental resets during normal terminal connections.3. Firmware Component: MCUboot and Serial RecoveryThe actual process of updating the nRF9151 firmware is handled by the MCUboot bootloader running on the nRF9151 itself. The "USB Flashing" perceived by the user is, in technical reality, a UART-based Serial Recovery session tunneled through the nRF5340's USB connection.3.1 MCUboot Architecture and PartitioningMCUboot is a secure, open-source bootloader designed for 32-bit microcontrollers. It divides the flash memory into distinct partitions:Slot 0 (Primary): Holds the active, runnable application image.Slot 1 (Secondary): Used as a staging area for new firmware images during an update.Scratch Partition: A small area used to safely swap images between Slot 0 and Slot 1.15On the nRF9151, which has 1 MB of flash, the partition layout is defined by the Partition Manager (part of the nRF Connect SDK build system). When a user initiates a USB flash, the new firmware binary is uploaded to Slot 1 via the UART interface. Once the upload is complete and the cryptographic signature is verified, MCUboot marks the image as "pending." On the next reboot, MCUboot swaps the contents of Slot 1 into Slot 0, effectively updating the application.3.2 Configuring Serial RecoveryStandard DFU often relies on the application itself to receive the update (e.g., via LTE or Wi-Fi) and write it to flash. However, if the application is broken or missing, the device needs a fail-safe recovery mechanism. This is Serial Recovery.In Serial Recovery mode, MCUboot does not immediately boot the application. Instead, it initializes a serial interface (UART) and enters a command loop, waiting for SMP (Simple Management Protocol) packets. This mode is essential for the "unbricking" capability implied by the user's request for USB flashing.To enable this on the nRF9151, specific configuration options must be added to the child_image/mcuboot.conf file associated with the nRF9151 project:Makefile# Enable Serial Recovery
CONFIG_MCUBOOT_SERIAL=y

# Select UART as the Transport
CONFIG_BOOT_SERIAL_UART=y
CONFIG_UART_CONSOLE=n  # Disable console to prevent interference

# Configure the Entry Trigger
CONFIG_BOOT_SERIAL_DETECT_PORT="GPIO"
CONFIG_BOOT_SERIAL_DETECT_PIN=26  # P0.26 (Button 1) 
CONFIG_BOOT_SERIAL_DETECT_PIN_VAL=0
CONFIG_BOOT_SERIAL_WAIT_FOR_DFU=y
CONFIG_BOOT_SERIAL_WAIT_FOR_DFU_TIMEOUT=500
3.3 The Mechanics of Serial Recovery EntryThe configuration above defines how the nRF9151 enters recovery mode. CONFIG_BOOT_SERIAL_DETECT_PIN=26 refers to Pin P0.26 on the nRF9151, which connects to Button 1 (SW3) on the Thingy:91 X.10The workflow for the user is:Hold down Button 1.Press the Reset button (SW4, accessible by removing the cover) OR trigger a software reset via the nRF5340 bridge.The nRF9151 reboots. MCUboot samples P0.26. Finding it Low (pressed), it halts the boot process and initializes the UART driver.The device is now ready to receive firmware via the mcumgr tool.The CONFIG_BOOT_SERIAL_WAIT_FOR_DFU option provides an alternative entry method without holding a button. With this enabled, MCUboot waits for a short duration (e.g., 500ms) after every reset to see if an MCUmgr packet is received. This is highly advantageous for automated testing rigs where physical button presses are impossible.4. Integration Strategy: Combining Bridge and ApplicationThe user's query implies a desire to add USB flashing "to my project." This suggests they are developing a custom application for the nRF5340 and/or nRF9151 and need to maintain the flashing capability. This creates a significant integration challenge: Resource Contention.4.1 Merging Functionality on the nRF5340If the user develops a custom nRF5340 application (e.g., a BLE sensor collector), they cannot simply "run" the Connectivity Bridge alongside it as a separate process. The nRF5340 runs a single Zephyr kernel instance. The bridge functionality must be merged into the user's application code.Step 1: Device Tree Overlay: The user's application must include a .overlay file that defines the CDC ACM nodes and maps them to the correct UART pins (VCOM0/VCOM1).Step 2: Kconfig Merging: The prj.conf of the user's application must include the USB stack and CDC ACM configurations detailed in Section 2.2.Step 3: Source Code Integration: The C code responsible for shuttling data between the USB and UART interfaces (typically found in main.c of the bridge sample) must be adapted into a dedicated thread or work item within the user's application.4.2 Handling Interrupt LatencyA critical aspect of this integration is interrupt priority management. The USB interrupt (handling bulk transfers) and the UART interrupt (handling flow control and data) must be serviced with low latency. If the user's custom application includes long-running interrupt service routines (ISRs) or disables interrupts for extended periods (e.g., for precise sensor timing), the data pipe for flashing may break. This results in packet timeouts and failed updates.To mitigate this, the bridge logic should utilize the Asynchronous UART API in Zephyr, which leverages the EasyDMA capabilities of the nRF5340.16 EasyDMA allows the UART peripheral to read/write directly to RAM without CPU intervention for every byte, significantly reducing the CPU load and susceptibility to interrupt latency.4.3 The "Lockout" Risk and RecoveryA common pitfall in this integration process is the "Lockout" scenario. If a developer flashes a custom nRF5340 image that contains a bug in the USB initialization code—or omits the USB stack entirely—the device will cease to enumerate as a USB device. At this point, the "USB Flashing" capability is lost, not just for the nRF5340 but also for the nRF9151, as the bridge is down.Recovery from this state requires external hardware. The user must connect an external J-Link debug probe to the P8 Debug Connector on the Thingy:91 X.17 Using the nrfutil or west flash --recover command, the user can erase the faulty firmware and restore the original Connectivity Bridge image. It is strongly recommended that developers maintain a "Golden Image" of the working bridge firmware to quickly recover from such situations.5. Toolchain and Operational WorkflowThe implementation of USB flashing is only useful if paired with the correct tooling on the host computer. The nRF Connect SDK ecosystem provides two primary tools for this purpose: nrfutil and mcumgr.5.1 nrfutil: The Unified Toolnrfutil is the modern command-line utility from Nordic Semiconductor. It is capable of recognizing the Thingy:91 X as a composite device and interacting with its various interfaces.Device Discovery: Running nrfutil device list will enumerate the connected Thingy:91 X, showing its serial number and available traits (e.g., serialPorts, mcuboot, jlink if an external probe is connected).17Programming: The nrfutil device program command abstracts much of the complexity. It can identify which COM port belongs to the nRF5340 and which acts as the bridge to the nRF9151.5.2 mcumgr: The Bootloader Clientmcumgr is the native client for MCUboot. It speaks the SMP protocol used for Serial Recovery.Connection: The user must define a connection profile that specifies the COM port and baud rate. E.g., mcumgr conn add acm0 type="serial" connstring="dev=/dev/ttyACM0,baud=115200".Image Upload: The command mcumgr image upload -c acm0 build/zephyr/app_update.bin initiates the transfer.18Image Listing: mcumgr image list -c acm0 allows the user to verify that the image has been successfully written to Slot 1 and to confirm the status of the update (pending, testing, active).5.3 Identifying the Correct COM PortThe Thingy:91 X exposes two COM ports. Identifying which one connects to the nRF9151's MCUboot is a common source of confusion.Heuristic: Typically, the lower-numbered COM port (e.g., COM4 vs COM5, or ttyACM0 vs ttyACM1) corresponds to CDC ACM 0, which maps to the primary UART of the nRF9151.Validation: A user can verify this by opening the port in a terminal emulator and resetting the Thingy:91 X. If the nRF9151 application is running, log output (e.g., "Booting Zephyr OS...") should appear on the primary port. If the device is in Serial Recovery, sending an mcumgr echo command should return a valid response.6. Security Implications: Trusted Firmware-M (TF-M)The nRF9151 utilizes the ARM TrustZone technology to separate Secure and Non-Secure processing environments. The application firmware updated via the USB bridge typically runs in the Non-Secure domain. However, the boot process is governed by Trusted Firmware-M (TF-M) running in the Secure domain.6.1 Image Signing and VerificationMCUboot performs signature verification on every image before booting it. This ensures that only authorized firmware can run on the device. When building the firmware using west build, the build system automatically signs the binary using a default development key (root-ec-p256.pem).19Production Warning: For a production project, the user must replace this default key with their own private key. If the bootloader on the device is provisioned with a production public key, it will reject any firmware signed with the development key. This rejection will occur silently during the boot process (the swap will simply not happen), leading to confusion.Bridge Transparency: The nRF5340 bridge is agnostic to the content of the firmware image. It transfers the encrypted and signed binary as a raw stream of bytes. The verification logic resides solely within MCUboot on the nRF9151.6.2 Updating the Bootloader ItselfUpdating the application is straightforward via Serial Recovery. Updating the bootloader (MCUboot) or the Secure Partition Manager (TF-M) is significantly more complex and risky. These components reside in immutable or protected regions of flash. Updating them typically requires a "Second Stage Bootloader" or a specific "Upgradable Bootloader" configuration that is not enabled by default. For most development scenarios, USB flashing should be restricted to the Non-Secure Application image to avoid the risk of permanently "bricking" the device's trust root.7. Strategic Recommendations and Future OutlookThe implementation of USB flashing on the Thingy:91 X is a sophisticated integration of hardware routing, firmware bridging, and bootloader configuration. It transforms the nRF5340 from a simple radio into a complex I/O processor.7.1 Recommendation: The "Passthrough" Build TargetTo streamline development, it is recommended to create a dedicated build target (e.g., thingy91x_bridge) in the user's CI/CD system. This target should compile the nRF5340 firmware with the Connectivity Bridge logic enabled but with minimal other features. This provides a "safe mode" firmware that can be flashed to the nRF5340 whenever reliable access to the nRF9151 is required for debugging or mass programming.7.2 Recommendation: Automated Testing IntegrationThe "Wait for DFU" capability of MCUboot (CONFIG_BOOT_SERIAL_WAIT_FOR_DFU) should be leveraged for automated testing. By configuring the nRF9151 to listen for DFU packets for 1-2 seconds after every boot, the user can create automated test scripts that update the firmware, run tests, and report results without any manual button presses or hardware intervention.7.3 Future Outlook: USB-C FeaturesThe nRF5340's USB peripheral is currently used primarily for CDC ACM. However, the USB-C connector on the Thingy:91 X supports Power Delivery (PD) negotiation via the nPM1300 PMIC. Future firmware updates to the Connectivity Bridge could leverage this to negotiate higher voltages (e.g., 9V or 12V) for faster battery charging or to support "Data Role Swap" scenarios where the Thingy:91 X could act as a USB host for external accessories, further expanding the utility of the platform.In conclusion, adding USB flashing to the Thingy:91 X is a multi-layered engineering task that requires a holistic understanding of the dual-chip architecture. By treating the nRF5340 as a software-defined bridge and correctly configuring the MCUboot transport layer, developers can achieve a seamless, single-cable development experience that rivals the convenience of traditional development kits while leveraging the advanced capabilities of the nRF9151 and nRF5340.8.
